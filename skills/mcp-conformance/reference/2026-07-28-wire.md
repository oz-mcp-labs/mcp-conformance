# The 2026-07-28 wire contract

What a server must do at the modern revision, and how to tell a modern request
from a legacy one. Every entry is checkable by hand against a live endpoint.

Source: the official changelog at
`https://modelcontextprotocol.io/specification/2026-07-28/changelog`. Where an
individual SEP page disagrees with the changelog, the changelog wins - the SEP
pages are stale on the renumbered error codes.

## What changed

| Area | 2025-11-25 | 2026-07-28 |
|---|---|---|
| Lifecycle | `initialize` / `notifications/initialized` | Removed. Stateless; every request self-describes. |
| Session | `Mcp-Session-Id` header | Removed. Server-minted handles as ordinary tool arguments. |
| Discovery | `initialize` result | `server/discover`, which servers **MUST** implement |
| Per-request identity | Negotiated once | `_meta` on every request |
| Routing | none | `Mcp-Method` / `Mcp-Name` required on POST |
| Server-initiated requests | `sampling/createMessage`, `elicitation/create`, `roots/list` | MRTR: `resultType: "input_required"` + `inputRequests`, client retries with `inputResponses` |
| Result envelope | none | `resultType` required on **every** result |
| Caching | none | `ttlMs` + `cacheScope` required on five methods |
| Change notifications | `resources/subscribe` + HTTP GET | `subscriptions/listen` |
| SSE resumability | `Last-Event-ID`, event ids | Removed. A broken stream loses the request; re-issue with a new id. |
| Tasks | experimental core | Extension `io.modelcontextprotocol/tasks` |

Also removed: `ping`, `logging/setLevel`, `notifications/roots/list_changed`.
Log level is per-request via `_meta` `io.modelcontextprotocol/logLevel`, and a
server **MUST NOT** emit `notifications/message` for a request that omitted it.

Deprecated (still functional, minimum twelve-month window): Roots, Sampling,
Logging; the HTTP+SSE transport; `includeContext` values `"thisServer"` and
`"allServers"`; OAuth Dynamic Client Registration, in favour of Client ID
Metadata Documents.

## Required `_meta` keys on a request

Namespaced under `io.modelcontextprotocol/`:

| Key | Requirement |
|---|---|
| `protocolVersion` | Required. Must equal the `MCP-Protocol-Version` header. |
| `clientCapabilities` | Required. |
| `clientInfo` | Clients **SHOULD** send it. |

Servers **SHOULD** identify themselves in each result's `_meta` as
`io.modelcontextprotocol/serverInfo`. Note this is in `_meta`, **not** a
top-level `serverInfo` - emitting it at the top level is a pre-release draft
shape that strict clients reject.

## Headers

| Header | On | Rule |
|---|---|---|
| `MCP-Protocol-Version` | every POST | must equal `_meta` `protocolVersion` |
| `Mcp-Method` | every request | must equal `method` |
| `Mcp-Name` | `tools/call`, `resources/read`, `prompts/get` | equals `params.name` or `params.uri` |

The point is gateway routing, metering and authorization without parsing the
body. `x-mcp-header` carries custom headers from tool parameters.

CORS: `Access-Control-Allow-Headers` matches literal names, so a prefix is not a
wildcard. Enumerate the concrete names or reflect them from
`Access-Control-Request-Headers`.

## Error codes

The server-error range is partitioned: `-32000`..`-32019` stays
implementation-defined (existing SDK usage grandfathered), `-32020`..`-32099` is
reserved for the specification.

| Code | Meaning | Was |
|---|---|---|
| `-32602` | resource not found (aligns with Invalid Params) | `-32002` |
| `-32020` | `HeaderMismatch` | `-32001` |
| `-32021` | `MissingRequiredClientCapability` | `-32003` |
| `-32022` | `UnsupportedProtocolVersion` | `-32004` |

`error.data.requiredCapabilities` on `-32021` is a `ClientCapabilities` **object**
keyed by the missing capability (`{ "sampling": {} }`), not an array of names.

Unknown and removed methods answer HTTP `404` with `-32601`.

## Cacheable results

`ttlMs` (nonnegative integer) and `cacheScope` (`"public"` or `"private"`) are
required on:

`tools/list`, `prompts/list`, `resources/list`, `resources/read`,
`resources/templates/list` - and on `server/discover`.

`"session"` is not a valid scope; it was a stale draft value. Servers **SHOULD**
return `tools/list` in a deterministic order, which also improves prompt-cache
hit rates.

## `server/discover`

The result carries `resultType: "complete"`, `supportedVersions` (modern
revisions only - do not mix legacy revisions in), `capabilities`, a nonnegative
integer `ttlMs`, `cacheScope`, and identity in
`_meta["io.modelcontextprotocol/serverInfo"]`.

The pre-release draft called the version list `protocolVersions` and put
`serverInfo` at the top level. Both are wrong in the final schema, and a strict
client rejects the response before it ever calls `tools/list`.

## Era detection

Per request. Keep no session state for it.

**Modern** when the `MCP-Protocol-Version` header carries a modern value, or
`_meta["io.modelcontextprotocol/protocolVersion"]` does, or the method is
modern-only (`server/discover`, `subscriptions/listen`).

**Legacy** when the method is `initialize`, or the version marker is
`2025-03-26` / `2025-06-18` / `2025-11-25`, or no era marker is present.

Three rules that are easy to get wrong:

1. **Header presence is not a signal.** Legacy Streamable HTTP clients from
   `2025-06-18` onward are required to send `MCP-Protocol-Version` on every
   post-initialize request. The value decides, never the presence.
2. **Compare lexicographically on the raw string, with no shape gate.**
   Revision strings are ISO dates, so `>=` orders them correctly, and an
   unparseable marker (`banana`, `draft`) then sorts *above* the floor: it lands
   in the modern branch and is answered `-32022`, instead of quietly receiving a
   legacy response. Gating on a `YYYY-MM-DD` shape first is how one runtime
   silently downgraded `MCP-Protocol-Version: banana`.
3. **The modern-only method set is a signal, not a claim of support.** A
   stateless surface declaring `resources: { subscribe: false, listChanged:
   false }` has nothing to stream and answers `subscriptions/listen` with
   `-32601`, like any other method it does not implement.

### `initialize` cannot reach the modern era

`initialize` with `protocolVersion: "2026-07-28"` answers `2025-11-25`, not the
requested revision. That follows from the rules above - `initialize` is always a
legacy request, and the modern revision is not in the legacy echo set - and it
is the legacy spec's own behaviour: reply with the latest revision supported on
that lifecycle.

The consequence is the part worth remembering. A spec-conformant client that
receives a revision it did not request either disconnects or pins itself to
`2025-11-25` for the session and never sends a modern marker again. **So a
hybrid client that opens with `initialize` can never reach the modern era.**
Reaching it is `server/discover`, or a modern version marker on any request.

Do not add `2026-07-28` to the legacy `initialize` echo set to work around this.
A modern version a surface does not support is answered `-32022` with a
`supported` list, never silently downgraded.

## Dual-era checklist

A server that must serve both eras - which is every server with real users,
since legacy clients cannot fall forward - needs all of:

1. CORS allow-lists carry `MCP-Protocol-Version`, `Mcp-Method` and `Mcp-Name`
   alongside the legacy headers, and keep `mcp-session-id` until legacy
   retirement.
2. Header/body mismatch rejected `400` + `-32020`, **gated on the detected
   era**. These headers do not exist in the legacy revisions, so a legacy
   request must ignore them the way it ignores any unknown header.
3. `server/discover` matching the final wire schema above.
4. `resultType` on every result; `ttlMs` + `cacheScope` on `server/discover` and
   the five cacheable methods.
5. Legacy lifecycle intact: `initialize` echoes the requested revision when
   supported, notifications answered `202`, session-id echo preserved.
6. Deterministic `tools/list` ordering.
7. Tests covering both eras on every surface change. One era passing is not
   evidence about the other.
